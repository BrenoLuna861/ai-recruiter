🔴 Críticos

2 achados — bloqueadores para ir ao ar
CRITICAL Credenciais reais expostas no arquivo _env versionado

O arquivo _env enviado contém a chave real da Anthropic, senhas do MySQL e MongoDB em texto puro. Se esse arquivo for commitado no repositório Git — mesmo em branch privado — qualquer pessoa com acesso ao repo pode usar essas credenciais.

Impacto: Comprometimento total da conta Anthropic (custos ilimitados de API), acesso irrestrito ao banco de dados e possível exfiltração de todos os dados de usuários.

✦ Correção imediata 
# 1. REVOGAR a chave Anthropic AGORA:
#    https://console.anthropic.com/settings/keys → Delete

# 2. Verificar se .env está no .gitignore
grep ".env" .gitignore

# 3. Se foi commitado, remover do histórico:
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch .env _env" \
  --prune-empty --tag-name-filter cat -- --all

# 4. Gerar novas senhas seguras:
openssl rand -base64 32   # para senhas de banco
openssl rand -base64 64   # para JWT_SECRET
CRITICAL JWT_SECRET fraco — minha-chave-secreta-super-longa-ai-recruiter-2024

O segredo JWT encontrado no _env é uma frase previsível e curta. Com ele, qualquer pessoa pode assinar tokens JWT válidos e se passar por qualquer usuário — incluindo ADMINs — sem conhecer a senha.

Impacto: Escalação de privilégios total, bypass completo de autenticação.

✦ Correção 
# Gere um segredo criptograficamente seguro (mínimo 512 bits):
openssl rand -base64 64

# Cole o output no .env:
JWT_SECRET=<output do comando acima>

# No application.yml, certifique-se de usar a variável:
jwt:
  secret: ${JWT_SECRET}
  expiration: 86400000    # 24h em ms
  refresh-expiration: 604800000  # 7d em ms

🟠 Altos

4 achados — corrigir antes do go-live
HIGH Coluna MySQL content trunca currículos — TEXT → deve ser LONGTEXT

O campo content da tabela resumes está como TEXT (limite de 65.535 bytes). Currículos em PDF extraídos para texto facilmente excedem esse limite. O erro Data truncation: Data too long for column 'content' confirma isso.

✦ Correção — já incluída no mysql-init.sql entregue 
-- Execute no banco existente:
ALTER TABLE resumes MODIFY COLUMN content LONGTEXT;

-- Na entidade JPA Resume.java:
@Lob
@Column(columnDefinition = "LONGTEXT")
private String content;
HIGH Portas 3306 (MySQL) e 27017 (MongoDB) expostas ao host em produção

O docker-compose.yml original expõe as portas dos bancos diretamente para o host com ports: "3306:3306". Qualquer pessoa com acesso ao IP da máquina pode tentar conexões diretas ao banco.

✦ Correção — já no docker-compose.yml entregue 
# Use 'expose' (interno) ao invés de 'ports' (host) para bancos:
mysql:
  expose:
    - "3306"    # Apenas containers na mesma rede acessam
  # ports:      # REMOVA isso em produção
  #   - "3306:3306"
HIGH Ausência de rate limiting em endpoints de autenticação

Sem rate limiting nos endpoints /api/auth/login e /api/auth/register, a aplicação está vulnerável a ataques de força bruta e credential stuffing. Um atacante pode tentar milhares de combinações sem qualquer limitação.

✦ Correção — já no nginx.conf entregue 
# No nginx.conf (já configurado):
limit_req_zone $binary_remote_addr zone=api_auth:10m rate=10r/m;

location /api/auth/login {
    limit_req zone=api_auth burst=5 nodelay;
    limit_req_status 429;
    ...
}

# No Spring Security (adicional):
# Implemente account lockout após 5 tentativas falhas
HIGH Ausência de HTTPS — aplicação rodando apenas em HTTP

Sem HTTPS, tokens JWT e senhas trafegam em texto puro. Qualquer interceptação de rede (man-in-the-middle) expõe credenciais de todos os usuários.

✦ Correção 
# Usando Certbot (Let's Encrypt — gratuito):
sudo apt install certbot python3-certbot-nginx
sudo certbot certonly --nginx -d seudominio.com -d www.seudominio.com

# Certificados gerados em:
# /etc/letsencrypt/live/seudominio.com/fullchain.pem
# /etc/letsencrypt/live/seudominio.com/privkey.pem

# Monte no container (docker-compose.yml — já configurado):
volumes:
  - /etc/letsencrypt/live/seudominio.com:/etc/ssl/ai-recruiter:ro

# Renovação automática:
sudo systemctl enable certbot.timer

🟡 Médios

5 achados — corrigir nas primeiras 2 semanas
MEDIUM Headers de segurança HTTP ausentes no Nginx original

Sem Content-Security-Policy, X-Frame-Options, X-Content-Type-Options e HSTS, a aplicação está vulnerável a XSS, clickjacking e MIME sniffing.

✦ Correção — já no nginx.conf entregue Todos os headers foram adicionados com valores seguros para produção.

MEDIUM Containers rodando com capabilities desnecessárias

Sem cap_drop: ALL e no-new-privileges, um processo comprometido dentro do container pode escalar privilégios no host Linux.

✦ Correção — já no docker-compose.yml entregue Todos os containers têm cap_drop: ALL com apenas as capabilities mínimas necessárias.

MEDIUM Validação de tipo de arquivo no upload de currículo apenas no cliente

Se a validação de tipo de arquivo (PDF, DOCX, TXT) ocorre apenas no frontend Vue, um atacante pode enviar qualquer arquivo via curl/Postman, incluindo executáveis ou scripts maliciosos.

✦ Correção — no ResumeService.java 
// Validar content-type e magic bytes no backend:
private static final Set<String> ALLOWED_TYPES = Set.of(
    "application/pdf",
    "application/vnd.openxmlformats-officedocument.wordprocessingml.document",
    "text/plain"
);
private static final long MAX_SIZE = 10 * 1024 * 1024; // 10MB

public void validateFile(MultipartFile file) {
    if (file.isEmpty() || file.getSize() > MAX_SIZE)
        throw new BadRequestException("Arquivo inválido ou muito grande");
    if (!ALLOWED_TYPES.contains(file.getContentType()))
        throw new BadRequestException("Tipo de arquivo não permitido");
}
MEDIUM Sem limite de recursos por container (memória / CPU)

Sem deploy.resources.limits, um único container com problema (ex: memory leak na JVM) pode consumir 100% dos recursos do host, derrubando os outros serviços.

✦ Correção — já no docker-compose.yml entregue Limites configurados: Backend 768MB/1.5 CPU, MySQL 512MB/1 CPU, MongoDB 512MB/1 CPU, Nginx 128MB/0.5 CPU.

MEDIUM Logs de erro expõem stack traces para o cliente

Em modo dev, o Spring Boot retorna stack traces completos nas respostas de erro HTTP. Isso pode revelar estrutura interna, versões de bibliotecas e caminhos do sistema.

✦ Correção — application-prod.yml 
server:
  error:
    include-stacktrace: never
    include-message: never
    include-binding-errors: never

# Global exception handler — retornar apenas mensagem genérica:
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleGeneric(Exception e) {
    log.error("Internal error", e); // Log interno completo
    return ResponseEntity.status(500)
        .body(new ErrorResponse("Erro interno. Tente novamente."));
}

✦ Solução recomendada 
# Cron para backup diário do MySQL:
0 2 * * * docker exec ai-recruiter-mysql \

# Manter 30 dias de histórico:
0 3 * * * find /backups -name "*.sql.gz" -mtime +30 -delete
